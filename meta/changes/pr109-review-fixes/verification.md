## Behavioural fixes: before and after

### Threads 25 and 49, nested debug locations and spans

Before (`firthCompile` on the `conditional` kernel program `false [42] [0]
if`): `debug_locations` held four top-level entries
(`{"instruction":i,"kernel_atom":i}` for `i` in 0..3) and nothing for the
literals inside either quotation body. After: six entries with `path` and
`kernel_path` `[0]`, `[1]`, `[1,0]`, `[2]`, `[2,0]`, `[3]`. The elaborate
adapter emitted no spans before; after, every checked word carries `spans`
(for `literal-int`: `[{"start":{"line":3,"column":3},"end":{"line":3,
"column":5}}]`), and a source-bound compile reports `source_path` and the
re-elaborated span on every debug entry. Tests: `debugLocationTests` in
`src/compiler/FirthCompilerTest.lean` (nested paths, two-level nesting,
source-bound spans, nested source-bound spans, supplied spans accepted only
when they match, kernel-only spans not reported, malformed span trees
refused) and the three `spans` cases in `src/agent/FirthElaborateTest.lean`.
Before this change the new test file did not compile against the base (no
`path` entries, no `spans` member).

### Thread 47, target bounds

Before: a 4097-atom body (`1` then 2048 `dup drop` pairs) compiled with
`status: success` and 4097 instructions, and 33 nested quotations followed
by 33 `call`s compiled with `status: success`; both are refused by the VM
decoder. After: both are `status: failure` with code
`firth.compile.target-bound-exceeded`; 4096 atoms and 32 levels compile.
Tests: `targetBoundTests` and the bound witnesses in `admissionWitnesses`
(`src/compiler/FirthCompilerTest.lean`); public corpus rows `bounds:
instruction count at 4096` (kernel-success), `bounds: instruction count above
4096` (reject), `bounds: quotation nesting at 32` (kernel-success), `bounds:
quotation nesting above 32` (reject) in
`tools/loop/check_compiler_admission.py`. The rows use a `bounds:` prefix so
the `--baseline` filter on `kernel:` rows is unchanged.

### Thread 16, `i64` boundary

Before: `Target.canonicalValue (.int 9223372036854775808)` encoded to the
ten-byte form `0080808080808080808002`, which the Rust reader refuses; the
lowering bound was an inline constant with no compiler-level test. After:
`Target.isInt64` states the domain, `lowerLiteral` uses it, and the tests
`i64 max zig-zag` (`00feffffffffffffffff01`, cross-checked against the Rust
reader's acceptance rule), the four `isInt64` witnesses, `i64 max literal
compiles` and `nat literal above i64 max is refused` pin both sides. The
`firthCompile` refusal of `9223372036854775808` was already
`firth.compile.unsupported-literal` before and after.

### Thread 26, capture well-formedness

Before: `Target.canonicalValue (.quotation [] [] [true])` and
`(.quotation [] [] [])` both encoded to `030000`. After:
`Target.wellFormedCode` refuses the mismatch at every depth, `compileWords`
reports it as `firth.compile.unsupported-value`, and the encoding witness
`one consumed capture` (`030001010002`) pins the section 7 order. Tests: the
five `wellFormedCode` witnesses in `admissionWitnesses`.

### Threads 31 and 40, row names

Before: a scheme with 25 row binders was refused with
`firth.compile.invalid-word-type` ("more row binders than canonical target
row names: 25"); `WordType.isRowName ","` and `isRowName " "` were `true` and
the predicate had no caller. After: the 25-binder word compiles to
`(forallρ,σ,τ,υ,φ,χ,ψ,ω,α,β,γ,δ,ε,ζ,η,θ,ι,κ,λ,μ,ν,ξ,π,ς,一;ρ--ρ,v0:Int^many)`,
the frozen table is unchanged, `isRowName` rejects delimiters, ASCII and
Unicode whitespace, and `render` checks every emitted name. Tests: the row
name and generator witnesses in `wordTypeWitnesses` (25 and 200 binders,
distinctness, frozen prefix, the block limit), `rows: 25 row binders` in
`check_compiler_admission.py`, and `25 row binders agree with the VM` in
`check_trust_boundaries.py`, which runs the compiled word through `vm-run`
and observed `[42]`.
